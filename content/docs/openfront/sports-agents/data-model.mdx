All lists are in `features/keystone/models`. Most use the helper `domainList` in `domainFields.ts`, which adds tracking fields, athlete scope, and write limits. The generated schema is `schema.graphql`. The checked-in migrations are in `migrations/`.

## Conventions

- Money is integer cents with a `currencyCode` (ISO 4217, default `USD`). Ledger and trust amounts are `bigInt`.
- Rates are basis points from 0 to 10000.
- Status fields cannot be set by generated writes. They change through commands.
- Every list has `createdAt` and `updatedAt`.
- Customer-facing numbers are random: `INV-` plus 16 hex characters.

| List | Key fields |
| --- | --- |

| `CommissionLedgerEntry` | `entryKey` (unique), `athlete`, `invoice`, `scheduledPayment`, `entryType`, `amountCents`, `payeeUser`, `reverses`, `reversalKey` (unique), `reason`, `preparedBy`, `approvedBy`, `occurredAt` |

| `ClientTrustAccount` | `athlete`, `name`, `currencyCode` |
| `ClientTrustEntry` | `account`, `athlete`, `invoice`, `entryType`, `amountCents`, `reference`, `reverses`, `reversalKey` (unique) |

Invoice statuses: `draft`, `sent`, `partially_paid`, `paid`, `void`, `written_off`. Invoice lines snapshot the description, gross, rate, and commission at the time of invoicing. A later change to the payment or contract does not alter a line.

Ledger entries and trust entries are append-only. A correction is an exact reversal, and the unique `reversalKey` makes a second reversal fail at the database.

## Payment lists

`PaymentProvider`, `PaymentCollection`, `PaymentSession`, `Payment`, `Refund`, and `PaymentWebhookEvent` come from the Restaurant lineage. A `Payment` points at its `CommissionInvoice` through `order`. A `PaymentCollection` points at an invoice. Providers keep credentials in a field that GraphQL never returns.

## Concurrency and replay

Every money command runs in one database transaction, takes a Postgres advisory lock on the athlete (`pg_advisory_xact_lock`), and records an idempotency key. The same key with a changed request is refused. A completed key replays the stored result. Status changes compare the current status first and fail if another request changed it.

`docs/REUSE.md` in the source repo lists which sibling Openfront products each piece was adapted from.
