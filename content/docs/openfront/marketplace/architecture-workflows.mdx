## Data model and tenancy

Marketplace has no database models. There is no Keystone schema, no Prisma client, and no migrations in use. Data lives in three places:

| Where | What |
|---|---|
| `marketplace.config.json` | The server's list of admitted stores: `baseUrl`, `platform`, optional `id` and `name`. |
| Connected stores | Products, menus, prices, regions, carts, customer accounts, payment sessions, orders. |
| Browser `localStorage` | Chat threads, cart IDs and proofs, store session tokens, store selection, AI settings, and marketplace name and theme. |

There is no tenant concept. Each deployment serves one store registry. Each browser keeps its own state. The `localStorage` keys are:

- `openfront_marketplace_chat_threads` for chat threads (text only, version 2);
- `openfront_marketplace_carts` for cart IDs and cart proofs, keyed by store ID;
- `openfront_marketplace_sessions` for store login tokens, keyed by store ID;
- `openfront_marketplace_config` for the buyer's store selection, order, and names;
- `openfront_marketplace_profile` for the marketplace name and theme.

## Routes

| Route | Purpose |
|---|---|
| `/` | The chat screen (`app/page.tsx`). |
| `/ethos` | A page that explains the open marketplace idea. |
| `POST /api/completion` | Runs the built-in AI chat and streams the reply. |
| `GET`, `POST /api/mcp-transport/[transport]` | The MCP server. Clients use `/api/mcp-transport/http`. `GET` returns the admitted store list. |
| `POST /api/ai-models` | Lists models from a custom OpenAI-compatible endpoint. Disabled when local AI is off. |
| `GET /api/marketplace/catalog` | Returns a small bundled mock catalog. It is labeled mock data and does not contact any store. |

There are no `/dashboard` routes. There is no account area, admin screen, or sign-in page.

## Code layout

- `app/page.tsx` and `features/marketplace/**`: the chat UI, store editor, cart dropdown, AI settings, setup dialog, and payment UI.
- `app/api/mcp-transport/tools/**`: MCP tool definitions and handlers.
- `app/api/mcp-transport/adapters/**`: one adapter per platform (`openfront`, `openfront-restaurant`) with GraphQL calls and MCP UI HTML.
- `app/api/mcp-transport/types/store-config.ts`: reads and validates `marketplace.config.json`.
- `lib/**`: source IDs, outbound fetch rules, request limits, browser storage, the model output filter, and MCP UI action rules.

## MCP tools

The transport lists these tools in `tools/list`:

| Group | Tools |
|---|---|
| Stores and regions | `getAvailableStores`, `getAvailableCountries`, `getAvailableRegions` |
| Discovery | `discoverProducts` (retail only), `discoverRestaurantMenus` (restaurant only), `getProduct` |
| Cart | `getOrCreateCart`, `createCart` (deprecated), `viewCart`, `getCart`, `addToCart`, `updateCartItem`, `removeCartItem` |
| Fulfillment | `setShippingAddress`, `setShippingMethod`, `setRestaurantFulfillment` |
| Checkout and payment | `validateCartForCheckout`, `getCheckoutLink`, `getAvailablePaymentMethods`, `initiatePaymentSession`, `completeCart` |
| Accounts | `loginUser` (shows a login form), `authenticateUser` (called by that form) |

Every `tools/call` is checked against the tool's input schema before any store request. Errors name the failing argument paths but never echo values.

The file `tools/graphql-tools.ts` defines generic GraphQL tools (`listModels`, `queryData`, and others). The transport does not import or expose them.

## What the model can call

The built-in chat gives the model only discovery tools: `getAvailableStores`, `getAvailableCountries`, `getAvailableRegions`, `discoverProducts`, `discoverRestaurantMenus`, and `getProduct`. Tool results are reduced to small safe summaries before the model sees them. HTML and metadata are dropped.

The route forces `getAvailableStores` on the first step. If the buyer's text clearly names retail or restaurant words, it forces the matching discovery tool on the second step. It stops when a tool returns a UI card, and after 10 steps at most.

Cart, address, shipping, payment, and login actions come from buttons inside MCP UI cards. The browser checks each action against the card it came from (`lib/mcp-action-policy.ts`). For example, a cart card for one store and cart can only call cart tools for that same store and cart.

## Store identity

Each store gets a stable ID derived from its HTTPS base URL and platform, for example `source-v2-openfront-https_3A_2F_2Fstore.example.com`. Changing the URL or platform changes the ID. Cart IDs, cart proofs, and session tokens are keyed by this ID, so one store's credentials are never sent to another.

Buyers can send their own store selection in the `x-marketplace-config` header (up to 20 entries). The server accepts it only if every entry matches an admitted store. Unknown, stale, or duplicate entries fail the whole request.

## Buyer workflow: retail store

1. The buyer asks for a product. The model calls `getAvailableStores` and `discoverProducts`.
2. A discovery card shows matching products. The buyer opens one (`getProduct`) and picks a variant.
3. `addToCart` reuses or creates a cart. A new Openfront cart is made with `createActiveCart`, which returns a cart proof. The browser saves the cart ID and proof.
4. The cart card shows items. The buyer changes quantities or removes items.
5. The buyer enters an address. `setShippingAddress` creates a guest user if needed. If the email already has an account, an email conflict card offers login, a different email, or the store checkout.
6. The buyer picks a shipping option (`setShippingMethod`).
7. The buyer pays with Stripe or PayPal in the chat (`initiatePaymentSession`, then `completeCart`), or opens `getCheckoutLink`. The link points to `<baseUrl>/<country>/account/checkout-link?cartId=...` on the store.

## Buyer workflow: restaurant

1. The model calls `discoverRestaurantMenus`. Cart buttons appear only if the store exposes the `createActiveCart` and `addActiveCartItem` mutations.
2. `addToCart` accepts `modifierIds`, `specialInstructions`, and `orderType` (`pickup` or `delivery`, default pickup).
3. `setRestaurantFulfillment` saves pickup or delivery details. Pickup needs name, email, and phone. Delivery also needs street, city, postal code, and a two-letter country code.
4. Before payment, the app checks for an empty cart, missing contact, missing delivery address, and an unmet delivery minimum.
5. Payment runs through `initiatePaymentSession` and `completeCart`. The restaurant checkout link is `<baseUrl>/checkout?cart_id=...`.

## Operator workflow

There is no operator dashboard. The operator:

1. edits `marketplace.config.json`;
2. sets AI environment variables, or leaves them unset for bring-your-own-key;
3. builds and deploys;
4. watches server logs. Tool failures log the tool name, store ID, and error name only.
