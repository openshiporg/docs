## Platform adapters

An adapter turns marketplace actions into GraphQL calls against one store. Adapters load from `app/api/mcp-transport/adapters/index.ts`:

| Platform | Adapter | Store type |
|---|---|---|
| `openfront` | `adapters/openfront` | Openfront E-commerce |
| `openfront-restaurant` | `adapters/openfront-restaurant` | Openfront Restaurant |

`shopify`, `bigcommerce`, and `woocommerce` appear in the platform type and have API paths, but no adapter exists. Calls for those stores throw "Unsupported platform".

Each adapter implements the `PlatformAdapter` interface in `adapters/types.ts`: product search and detail, cart create/read/update, shipping options, address, login and cart connect, checkout link, payment methods, payment session, cart completion, store info, countries, and optional MCP UI generators.

## Named GraphQL operations

### Openfront E-commerce adapter

| Operation | Used for |
|---|---|
| `SearchProducts` | Product list for discovery. |
| `GetProduct` | Product detail and variants. |
| unnamed `regions` query | Find the region for a country before creating a cart, and list countries. |
| `CreateActiveCart` | Create a guest cart. Must return an `id` and a `proof`. |
| `AddToCart`, `UpdateActiveCart`, `RemoveCartItem` | Change cart contents through `updateActiveCart`. |
| `UpdateLineItem` | Change a line quantity (`updateActiveCartLineItem`). |
| `GetCart` | Read the cart (`activeCart`) and shipping options (`activeCartShippingOptions`). |
| `AddShippingMethod` | Select a shipping option (`addActiveCartShippingMethod`). |
| `CheckEmail`, `CreateGuestUser`, `AuthenticateGuestUser`, `CreateAddress` | Guest checkout address flow. |
| `AuthenticateUser`, `Me` | Customer login (`authenticateUserWithPassword`) and current user. |
| `ListPaymentProviders` | Payment providers for a region (`activeCartPaymentProviders`). |
| `InitiatePaymentSession` | Start a Stripe or PayPal session. |
| `CompleteActiveCart` | Turn the cart into an order after payment. |
| `GetStore` | Store name, logo, and payment provider publishable keys. |

Guest cart requests send the cart proof in an `X-Openfront-Cart-Proof` header.

### Openfront Restaurant adapter

| Operation | Used for |
|---|---|
| `MarketplaceRestaurantMenu`, `MarketplaceMenuItem` | Menu list and item detail. |
| `MarketplaceRestaurantCartCapability` | Checks that `createActiveCart` and `addActiveCartItem` exist before showing cart buttons. |
| `MarketplaceCreateRestaurantCart`, `MarketplaceRestaurantCart` | Create and read a cart. |
| `MarketplaceAddRestaurantItem`, `MarketplaceUpdateRestaurantItem`, `MarketplaceRemoveRestaurantItem` | Change cart contents. |
| `MarketplaceUpdateRestaurantFulfillment`, `MarketplaceSetRestaurantDelivery` | Save pickup or delivery details. |
| `MarketplaceRestaurantLogin`, `MarketplaceConnectRestaurantCart` | Customer login and attaching the cart. |
| `MarketplaceRestaurantPaymentMethods`, `MarketplaceInitiateRestaurantPayment`, `MarketplaceCompleteRestaurantCart` | Payment and order completion. |
| `MarketplaceRestaurantInfo`, `MarketplaceRestaurantLegacyFulfillmentInfo`, `MarketplaceRestaurantLegacyInfo`, `MarketplaceRestaurantCountry` | Store settings, delivery rules, and country. Legacy queries support older restaurant schemas. |

Restaurant cart requests send the cart proof in an `X-Restaurant-Cart-Proof` header and the `_restaurant_cart_id` cookie.

## Outbound request rules

All store requests go through `createTrustedFetch` in `lib/remote-endpoint.ts`:

- Only origins from `marketplace.config.json` are allowed.
- HTTPS only, no credentials in the URL.
- Every DNS answer must be a public address. Private and reserved IPv4 and IPv6 ranges are refused.
- The checked address is pinned to the socket, and TLS hostname checks stay on.
- Redirects are refused.
- Each store call times out after 8 seconds. GraphQL responses are capped at 2 MiB (8 MiB for introspection).
- In non-production builds only, `.local` and `.localhost` stores listed in the config are allowed over HTTP.

The marketplace's own cookies are not forwarded to stores. A bearer token is only attached for the store named in the tool call.

## AI providers

The built-in chat supports two providers:

- **OpenRouter**, with the operator's key (shared mode) or the buyer's key (local mode).
- **Custom**, any OpenAI-compatible endpoint the buyer enters. It goes through the same outbound rules. `MARKETPLACE_CUSTOM_AI_ORIGINS` can limit which origins are allowed.

The model only sees discovery tools and filtered tool output. Cart IDs, proofs, session tokens, card HTML, and addresses are kept out of model messages. Replayed chat history is text only.

External MCP clients connect to `/api/mcp-transport/http` and get the full tool list. They must store cart IDs, proofs, and tokens per store and send them back in headers.

## Payments

Stores provide payment. The marketplace:

1. reads the store's payment providers and publishable keys (`GetStore`);
2. asks the store to start a payment session (`initiatePaymentSession`);
3. renders Stripe card elements or PayPal buttons in the browser with the store's publishable key;
4. after the buyer pays, calls `completeCart` so the store creates the order.

Card data goes from the browser to Stripe or PayPal. The marketplace does not see it and takes no fee.

The other path is `getCheckoutLink`, which sends the buyer to the store's own checkout page.

## Adding an adapter

1. Add the platform name to `SourcePlatform` in `lib/source-identity.ts` and its API path in `types/store-config.ts`.
2. Implement `PlatformAdapter` in a new folder under `app/api/mcp-transport/adapters/`.
3. Register it in `adapters/index.ts`.
4. Add cart proof handling in `tools/utils.ts` if the platform uses guest cart proofs. Unknown platforms are refused a proof.
5. Add tests for store IDs, cart proofs, and wrong-store requests.
