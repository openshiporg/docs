## Adapters

- Only Openfront E-commerce (`openfront`) and Openfront Restaurant (`openfront-restaurant`) stores work.
- `shopify`, `bigcommerce`, and `woocommerce` are listed as platform names but have no adapter. The README mentions them as future work.
- Other Openfront products (grocery, hotel, salon, gym, pharmacy, and so on) are not supported. The prompt suggestions list them, but only E-commerce and Restaurant are marked available.
- There is no shared adapter test suite. Store health, version checks, and a per-store disable switch do not exist.

## No operator dashboard or database

- There is no admin UI, sign-in, user model, or role system. The store registry is a JSON file edited by hand and redeployed.
- The `app/dashboard`, `features/keystone`, `features/platform`, and `migrations` folders in a local checkout are empty. No models, platform pages, or migrations are in use.
- Nothing is stored server-side: no order history, analytics, audit log, or buyer accounts.

## Discovery

- Product search does not send the query to the store. The adapter fetches up to 50 public products or menu items per store, then matches keywords locally. Items beyond that first page are never searched.
- Location filtering only matches stores that publish address or country data. Stores without it are left out of location searches.
- The route picks a discovery tool from fixed keyword lists. Unusual wording may not force discovery.
- `/api/marketplace/catalog` returns bundled mock data, not live stores.

## Browser state

- Chat threads, cart IDs, cart proofs, store session tokens, store selection, AI settings, and local API keys are kept in `localStorage`. Anyone with access to the browser profile, an extension, or a script injection could read them.
- There is no sync across devices and no remote sign-out.
- Store session tokens are stored as issued by the store. The marketplace does not encrypt or expire them itself.
- MCP UI cards are HTML from the adapters, rendered in iframes. The browser limits which tools each card can call, but card content still includes store data.

## AI

- Model answers can be wrong. Prices, stock, and shipping should be read from the store cards, not from model text.
- In local mode, the buyer's API key is sent to `/api/completion` on every request.
- A custom AI endpoint can be any public HTTPS origin unless `MARKETPLACE_CUSTOM_AI_ORIGINS` is set.
- External MCP clients get the full tool list, including cart and payment tools. They are responsible for storing per-store credentials safely.

## Checkout and payment

- In-chat payment supports Stripe and PayPal only, and only when the store has them configured with publishable keys.
- The marketplace trusts the store to validate cart ownership, price, stock, tax, and payment. It does not reconcile orders afterward.
- `createCart` is deprecated but still listed in `tools/list`.

## Operations

- No rate limiting, bot protection, or abuse controls are built in. Request size limits exist (128 KiB for MCP requests, 256 KiB for completion requests), and store calls time out after 8 seconds.
- Logs record tool names, store IDs, operation names, and error names only. There are no metrics or alerts.
- Tests are Node unit tests. There are no browser end-to-end tests against real stores.
