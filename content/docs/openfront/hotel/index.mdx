Openfront Hotel is a self-hostable hotel property-management and direct-booking application for one property. Guests browse rooms, get a stay quote, book direct, and review their booking and folio. Staff use the dashboard for reservations, room assignment, rates, housekeeping, maintenance, folios, cashier work, receivables, group blocks, and night audit.

It is built with Next.js 16, React 19, Keystone 6, Prisma, and PostgreSQL. Start with [Getting started](/docs/openfront/hotel/getting-started).

<Callout type="warn">
One database holds one property. There is no Organization, Property, or Location model. `HotelSettings` is a singleton row, roles are global, and the property key `the-alder-house` is a fixed constant used to label audit, outbox, business-date, and night-audit records. There are no native Booking.com or Expedia adapters.
</Callout>

Some features have no list of their own. Cashier shifts, receivable accounts and invoices, approvals, stay services, room outages, relocations, the stay register, and guest-governance requests are stored as `HotelAuditEvent` rows with an `aggregateType`, and read back through named queries.

`Booking`, `ReservationLineItem`, and `FolioEntry` deny create, update, and delete through generated CRUD. Changes go through named commands. Bookings store snapshot amounts in integer minor units (`totalAmountMinor`, `balanceDueMinor`, and so on). Older `Float` fields such as `totalAmount` and `roomRate` still exist on `Booking`, so the schema is not fully fixed-point.

## Roles

The first user created at `/dashboard/init` gets an `Admin` role with every flag. Role flags are:

`canAccessDashboard`, `canManageRooms`, `canManageBookings`, `canManageHousekeeping`, `canManageGuests`, `canManagePayments`, `canSeeOtherPeople`, `canEditOtherPeople`, `canManagePeople`, `canManageRoles`, `canManageOnboarding`, `canManageAudit`, `canManageGuestPrivacy`, `canApproveHotelExceptions`, `canManageIntegrations`.

Staff can enable TOTP MFA with recovery codes at `/dashboard/platform/security`. Guest accounts are `User` rows with no role. Dashboard sign-up is closed unless `PUBLIC_SIGNUPS_ALLOWED=true`.

## Guest access

A guest proves access with confirmation number and email (`verifyGuestBooking`) or by signing in to a guest account. Access is kept in an HMAC-signed `hotel-guest-access` cookie that lasts 30 days and holds at most 20 bookings. It is signed with `GUEST_ACCESS_SECRET`, falling back to `SESSION_SECRET` and then `NEXTAUTH_SECRET`. Guest queries recheck the cookie on every call.

A storefront booking starts as a `pending` hold that expires after 30 minutes. A worker cancels expired holds. The booking needs a signed quote from `storefrontQuote` (signed with `HOTEL_QUOTE_SECRET`).

## Onboarding

`runHotelOnboarding` needs `canManageOnboarding`. It runs in one serializable transaction under a Postgres advisory lock. Templates:

- `full` — The Alder House: 3 room types, 8 rooms, 4 rate plans, 2 seasonal rates, 3 guests, 3 bookings, 2 payments, housekeeping and maintenance rows, 2 channels, loyalty, and inventory.
- `minimal` — a smaller subset: 2 room types, 5 rooms, 2 rate plans, 1 seasonal rate, 1 guest, 1 booking and payment, 1 housekeeping task, 1 maintenance request, 1 channel, and 2 inventory rows.
- `custom` — your own JSON, checked against the onboarding schema.

For `full` and `minimal`, seed dates are moved relative to the property business date; `custom` dates are kept as given. Seeded channels (named Booking.com and Expedia) are inactive and use `mode: demo`, so they never call a remote endpoint. Onboarding refuses to run if the database already has rooms, room types, bookings, folios, housekeeping tasks, maintenance requests, guests, rate plans, channels, inventory rows, night audits, or seed records. Running it again with the same input is a no-op; with different input it fails. After setup, change data through property settings and the workspaces.

## Payments

Two payment adapters are registered: Stripe (`pp_stripe_stripe`) and PayPal (`pp_paypal_paypal`). Configure them at `/dashboard/platform/payment-providers` (needs `canManagePayments` and `canManageIntegrations`). Credentials are encrypted with `HOTEL_DATA_ENCRYPTION_KEY` and are not shown again. A Stripe record with no stored credentials can fall back to `STRIPE_SECRET_KEY`, `STRIPE_PUBLISHABLE_KEY`, and `STRIPE_WEBHOOK_SECRET` when `STRIPE_ENABLED=true`.

Provider webhooks enter at `/api/payment-providers/[providerCode]/webhook`. Staff can record offline payments on a folio with `recordBookingPayment`. Stripe disputes are tracked at `/dashboard/platform/disputes`; evidence is submitted in the Stripe dashboard, not from this app.

## Channels

Channel support is a generic HTTP bridge, not an OTA integration. Each `Channel` stores a `mode` in its credentials: `disabled`, `demo`, or `live`. Only `live` channels send requests. A live channel needs HTTPS endpoints whose origins are listed in `allowedOrigins`. Inbound reservations arrive at `/api/webhooks/channel/[channelId]`, which requires live mode, an HMAC signature header, and a signed event id used for replay protection. Rate sync is not implemented. The dashboard Channels page says channels are off by default.

## Workers and outbox

`instrumentation.ts` starts four in-process workers in the Node.js runtime (not during build or tests):

- channel sync: inventory push every 15 minutes, reservation pull every 5 minutes, retries every 2 minutes, live channels only;
- outbox delivery: starts only when SMTP is fully configured or `HOTEL_OUTBOX_DISPATCH_URL`, `HOTEL_OUTBOX_DISPATCH_SECRET`, and `HOTEL_OUTBOX_DISPATCH_CREDENTIAL_KEY_ID` are all set;
- refund intents;
- expiry of booking holds and group block release dates.

Workers take database leases (`HotelWorkerLease`), so only one process runs each job at a time. Guest emails (confirmation, update, cancellation, refund, no-show, pre-arrival, modification response, contact receipt) are queued as outbox events. Without SMTP or an HTTP dispatcher, they stay pending.

## Other endpoints

- `/api/health` returns a static OK. `/api/ready` checks settings, business date, providers, and worker progress.
- `/api/hotel/outbox/receiver` accepts HMAC-signed events only when `HOTEL_OUTBOX_RECEIVER_SECRET` and `HOTEL_OUTBOX_RECEIVER_CREDENTIAL_KEY_ID` are set.
- `/api/completion` is the dashboard AI chat. It needs a signed-in user with `canAccessDashboard` plus `OPENROUTER_API_KEY` and `OPENROUTER_MODEL`.
- `/api/mcp-transport/[transport]` returns HTTP 410. MCP machine access is disabled until scoped machine authentication exists. `/api/completion` opens an MCP client against this endpoint for its tools, so the dashboard AI chat is expected to fail in current source.
- `/api/create-payment-intent` and `/api/send-booking-confirmation` return HTTP 410. Use the booking payment session and outbox paths instead.

## Limitations

- One property per database. No multi-property tenancy.
- No native OTA adapters and no rate sync. Seeded channels are demo rows.
- Email depends on SMTP or an external dispatcher. Queued outbox rows are not proof of delivery.
- Image upload needs all five `S3_*` variables. Without them, room images can only use public paths.
- Booking money fields are partly `Float` and partly integer minor units.
- MCP transport is disabled, so the dashboard AI chat cannot reach its tools.
- Workers run inside the web process. A serverless deploy with no long-running process will not run them.
- The repository has only two test files under `tests/`. Test booking concurrency, guest access, payments, refunds, night audit, and workers on your own deployment before handling real guests or money.
- No compliance or certification is claimed.
